## Access review

Today the checked-in Compose configuration uses a single login `sahyog` for the database and API; `build_postgres_deps` uses the same DATABASE_URL for its graph/checkpointer and tool pools. Migrations 001–007 create no scoped application roles or GRANT/REVOKE policy. A read-only inventory on localhost:55432 on 2026-11-02 found current user/database `sahyog`/`sahyog` and one non-system role: `sahyog`, with LOGIN, SUPERUSER, CREATEROLE and CREATEDB all true. Built-in `pg_*` roles were excluded from that inventory. This says nothing about a remote deployment. No periodic access-review process is implemented.

Architect target roles:

| Role | Required access |
| --- | --- |
| `sahyog_owner` (NOLOGIN) | Own schema/functions; no application credentials. |
| `sahyog_migrator` | Time-limited migration privilege, separate from runtime; reviewed deployment access. |
| `sahyog_scheduler` | Read directory/slots; constrained execution of book/release functions; no arbitrary note/audit writes or DDL. |
| `sahyog_records_reader` | Scoped records/consent reads with patient authorization enforced independently; no bulk unrestricted patient reads. |
| `sahyog_ingest` | Insert/update document ingest state and chunks; no scheduling/signature privileges. |
| `sahyog_checkpoint` | Only runtime checkpoint tables; purge permissions separately controlled. |
| `sahyog_note_signer` | Doctor-authorized signed-note insert/version operation; no update/delete or trigger bypass. |
| `sahyog_audit_writer` / `sahyog_auditor` | Append-only audit insert / approved read-only access to audit views; separate identities. |
| `sahyog_ops` / backup role | Scoped monitoring/backup with reviewed expiry; no routine owner credentials. |

Role separation needs pool/credential separation, restricted function permissions, and a patient-scope enforcement strategy; role names alone do not enforce authorization. Review owners should inventory login/service identities, memberships, grants, object ownership, active sessions, backup access and secrets; remove stale access, approve exceptions and retain dated evidence. Perform before production, on staff departure and at least quarterly. This cadence is proposed, not an existing automated control.

## Final Pro disposition

W3 text-transcript review/signing, durable owner-scoped ingest queue and separate worker,
allowlisted Postgres tracing, and shared Presidio/token-map egress controls are built.
Queue controls are exercised in `services/api/tests/test_upload_postgres.py`; implementation:
`services/api/main.py` and `services/records/worker.py`. The queue does not establish
malware scanning, encryption or production identity. Tracing retention has a purge command,
not a scheduled retention guarantee. W3 has no audio or speech-to-text lifecycle to certify.
The saved [W2 run 20261103-104837](../evals/runs/w2-20261103-104837.json) records a red-team pass;
below-target faithfulness and the [earlier human judge review](../evals/runs/judge-review-w2-20261103-094651.md)
remain limitations, not closed threats. Architect controls remain not yet built; OTP/OIDC,
SMS delivery and timeout scheduling remain open Pro gaps. No residual risk above is waived by the tier label.
